## The web app (PWA) — how AllWebMails enters the market
- **One app for every device**, at **https://app.allwebmails.com**. It's built from the same code as the Android app, works in any modern browser, and can be **installed** like an app:
  - Android: Chrome → Install app.
  - Windows and Mac: Chrome or Edge.
  - iPhone and iPad: Safari → Share → Add to Home Screen.
- **Notifications** use standard Web Push. As on the phone, they say only "New email received at …". On iPhone they work from iOS 16.4 when the app is added to the home screen.
- **Security in the browser:**
  - **Sessions:** the long-lived sign-in token sits in an HttpOnly, SameSite=Strict cookie that page scripts can't read, and it can only be used together with the app's own request header. The short-lived access token is kept in memory only.
  - **Mail display:** mail is shown in a sandboxed frame with a separate, opaque origin. The page's Content-Security-Policy allows only the app's own code plus three fixed helper scripts, each allowed by its exact hash. A `<script>` hidden in an email cannot run; the browser test checks this.
  - **Links:** a link click in mail is passed to the app, which shows the same "check where this link goes" warning as on the phone.
  - **Nothing private stays in the browser:** mail is cached in memory only for the open tab, and the service worker caches only the app's own files, never mail or API responses. That makes it safe on shared or public computers.
- **Same server, same address:** the API server also serves the web app, so there's no cross-site setup. The Android app uses the same address.

## Android app (APK, no Play Store)
- The app is now named **AllWebMails** (`com.allwebmails.app`) and has a new icon.
- It's built with `eas build -p android --profile preview` and downloaded from **allwebmails.com/download**.
- It checks the server for updates. When a newer version exists it shows a banner. Below the minimum supported version it asks the user to update first. Both versions are set with `LATEST_APP_VERSION` and `MIN_APP_VERSION`.

## Deployment
- `deploy/server/`:
  - Dockerfile (non-root, includes `pg_dump` 17 for backups) and docker-compose: web app + API, admin site, sync worker, scheduler, Caddy for automatic HTTPS, optional ClamAV;
  - `env.example` and a smoke test.
- **`docs/deploy.md`** is the step-by-step guide:
  - DNS records in hPanel;
  - Supabase, Neon or local PostgreSQL, with SQL for the database users;
  - server setup, secrets as files, migrations, creating the admin;
  - website upload, APK builds and updates;
  - backups, monitoring, updates, and a launch checklist.
- **Monitoring:**
  - `/healthz` shows the process is up.
  - `/readyz` checks the database.
  - `/healthz/jobs` returns 503 when mail sync or the scheduler stops. Point an uptime monitor at it.
  - Background jobs record heartbeats, which the admin dashboard shows.
- **CI** has three jobs:
  - backend tests on PostgreSQL 13 and 16;
  - Android and web builds;
  - **browser end-to-end** (the real web build in Chromium) and a **server image** build with smoke test.

3. Upload `deploy/website/` to `public_html`.
4. Build and upload the APK.
5. Work through the launch checklist at the end of docs/deploy.md.

## Known limitations
- **Offline in the browser:** the web app works offline only for what was opened in the current tab. It doesn't keep mail after the tab closes, by design. The Android app keeps an encrypted offline copy.
- **Notifications:** web push needs the browser's permission. On iPhone it needs iOS 16.4+ and the home-screen app.
- **Attachments on iPhone:** downloads use the browser's normal download, so on iPhone they open in the Files and Safari preview.
- **Not yet done (M4b):** connecting Gmail and Outlook mailboxes with "Sign in with Google/Microsoft" (OAuth) needs app registrations with Google and Microsoft. Until then, those mailboxes work with an app password over IMAP and SMTP.
