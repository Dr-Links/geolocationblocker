# Milestone 8: Storage and data lifecycle

**Status:** built. 103 backend tests pass, including 10 new storage tests. The app and the admin site build.

## What it does

- **Usage accounting:**
  - Each user's storage is counted automatically: saved message text, saved files (attachments and uploads), plus an estimate of 2 KB per message for headers and the search index.
  - Users see it under *Home → Storage*, broken down by mailbox. The admin sees it per user and on the dashboard.
- **Quota:** the platform default is 5 GB. The admin can change it per user (User detail) or for everyone (Settings).
  - **Above 80 %:** a warning on the home screen and one push notification.
  - **Full:**
    - New mail **still arrives and still notifies**, and the headers still sync. Its text and attachments just aren't saved here: they're loaded from the mail server when opened.
    - New uploads are refused with "Your storage is full".
    - Sending still works.
    - Nothing on the user's mail server is ever touched.
  - Warnings are sent once per level, not repeatedly.
- **Automatic eviction:**
  - Only removes copies that can be fetched again: the text and cached attachments of messages **still on the mail server**.
  - Messages already deleted on the server, where the copy here is the only one, are **never** evicted automatically.
  - **Retention setting** (user's choice: keep everything, 30 days, 90 days, 6 months, 1 year). Older text isn't stored, and text already stored is removed by housekeeping.
  - **Quota pressure:** above 95 %, the oldest re-fetchable copies are removed until usage is about 85 %. Cached attachments go first, then message text.
  - Search still finds evicted messages, because the search index is kept.
- **Freeing space by hand:** "Remove messages already deleted on the server" deletes the copies kept only here, after a confirmation that explains they're the last copies.
- **File cleanup:**
  - Files nothing refers to any more (deleted uploads, evicted copies, deleted mailboxes) are deleted after one hour, both the database row and the stored object.
  - A failed object delete is retried with backoff, so storage never silently leaks.
- **Mailbox delete (purge)** removes that mailbox's mail and files. Identical files still used by another mailbox of the same user are kept, and other mailboxes are untouched (tested).
- **S3-compatible file storage** (AWS S3, Cloudflare R2, Backblaze B2, Wasabi, MinIO), as an alternative to the local disk:
  - Files are encrypted with the user's key **before** upload, so the storage provider only sees ciphertext.
  - Requests are signed with AWS Signature V4. The signing is checked against AWS's published example and against the official AWS SDK (botocore).

Housekeeping runs as part of every `cron` run (scheduler tick).

## Settings (env file)

| Setting | Meaning |
|---|---|
| `BLOB_DRIVER` | `local` (default, uses `BLOB_DIR`) or `s3` |
| `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_PREFIX` | object storage location (`S3_REGION=auto` for R2) |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | **secrets**: put them in the env file (or `*_FILE`), never in chat |

**Changing driver doesn't move existing files.** Choose before going live, or copy the `u/…` objects across with a tool such as `rclone` first.

## What you test

1. In the admin site, set your test user's quota to 0.01 GB. Send mail to the mailbox: it arrives, but opening it loads the text live. The app shows "Storage is full", and attaching a file is refused.
2. Raise the quota again. New mail is saved as usual.
3. Set retention to 30 days. Within a cron run or two, old messages still on the server show "loading" briefly when opened.
4. Connect two mailboxes, then delete one with "delete everything". The other mailbox's mail and attachments are intact.

## Known limitations

- Usage is an estimate. The 2 KB per message for metadata and search index is a flat figure, not measured.
- The S3 driver was tested against s3rver, a local S3 emulator. s3rver doesn't verify V4 signatures, so signature correctness is checked against AWS's own reference values instead. Test it once with your real bucket before going live.
- There's no automatic migration between the local disk and S3.
