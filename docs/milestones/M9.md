# Milestone 9: Security warnings, block lists, reminders, virus scanning, backups and monitoring

**Status:** built. 113 backend tests pass, including 11 new ones covering phishing, block lists, reminders, ClamAV and backup/restore. The app and the admin site build.

## What it does

### Phishing and spoofing warnings
Every message is checked when it arrives. The checks only **warn**: they never hide or delete mail.

| Warning | Example |
|---|---|
| Sender verification failed | DMARC fail (likely forged), or SPF fail without a valid DKIM signature |
| Fake address in the sender name | Name shows `support@paypal.com` but the mail came from `x@other.example` |
| Lookalike sender or link domain | `paypa1.com`, `g00gle.net`, `rnicrosoft.com`, Cyrillic letters, `paypal-secure-login.com` |
| Link shows one site, opens another | Text `https://www.paypal.com`, link goes to `evil.example` |
| Link to a bare IP address | `http://192.0.2.7/...` |
| Replies go elsewhere | Reply-To domain differs from the sender's |
| Dangerous attachment, or malware found | `.exe` / `.js` / disguised programs, or a ClamAV hit |

The app shows a red ("looks dangerous") or orange ("be careful") box with the reasons in plain language, plus ⚠ in the message list.

### Block lists
- **The user's own:** tap *Block sender* on a message, either that address or everyone at the domain. It can also be managed under *Home → Blocked senders*.
- **Platform-wide, managed by the admin** (*Admin → Blocklist*), for known phishing campaigns.
- New mail from a blocked sender is **moved to the Junk folder on the mail server**, marked as blocked, and **no notification is sent**. Nothing is deleted.
- A user can't block one of their own mailboxes.

### Follow-up reminders
- *Remind me* on any message: in 3 hours, tomorrow morning, in 3 days, or next Monday.
- Optionally "**only if nobody replies**": cancelled automatically when someone else answers in the conversation.
- The push notification says only "Reminder: follow up on a message in sales@company.com". It never includes the subject, the sender or your note.
- *Home → Reminders* lists upcoming reminders and those from the last 30 days.

### Virus scanning (optional, ClamAV)
If `CLAMAV_HOST` is set:
- Uploads are scanned before they're stored; infected files are refused.
- Received attachments are scanned the first time they're opened. If one is infected, the download is blocked, the result is remembered, and the message is marked dangerous.
- `CLAMAV_REQUIRED=true` refuses files while the scanner is down. By default they're allowed through and the error is recorded.
- ClamAV needs about 1–2 GB of RAM, so it suits a VPS rather than shared hosting.

### Backups and the deletion ledger
- `node dist/cli.js backup:run` makes an **encrypted** backup of the database (AES-256-GCM with `BACKUP_KEY`). It stores it in a local folder or an S3-compatible bucket and keeps the newest `BACKUP_KEEP` (default 14).
- Stored files aren't included: they're encrypted per user and live in their own store. Back that up with your storage provider's versioning or replication.
- **Deletion ledger:** permanently deleting a user is first recorded *outside* the database, in `ledger/` next to the backups. If the ledger can't be written, nothing is deleted.
  - After any restore, `backup:reapply-deletions` deletes those users again.
  - Their keys go with them, so their files stay unreadable even if the files are restored.
- `backup:restore-test` restores the newest backup into an empty scratch database (`DB_NAME_SCRATCH`), re-applies deletions and reports what came back. Run it monthly. The test suite does the same: it deletes a user after a backup, restores, and confirms the user stays deleted and that database permissions survive.
- `backup:list` and `backup:fetch <name> <file>` download and decrypt a backup for `pg_restore`.

Suggested cron (daily at 03:17):
```
17 3 * * * cd /path/to/api && ENV_FILE=/path/to/emailplatform.env node dist/cli.js backup:run >> /path/to/backup.log 2>&1
```

### Admin monitoring
The dashboard has a new **System health** panel:
- last successful backup, flagged if older than 26 hours, and the last backup error;
- messages waiting to send and their age;
- sends with an unknown outcome;
- mailboxes not synced for 30+ minutes;
- failed mailbox actions, pending or failed notifications, overdue reminders, the file-deletion backlog, and infected attachments.

## What you need to do
1. Run `keys:generate` and put `BACKUP_KEY` in the env file. **Keep a copy somewhere other than the server** (a password manager), or backups can't be read. Never paste it in chat.
2. Make sure `pg_dump` is installed on the server, the same or a newer major version than your database. With a hosted database (Supabase or Neon), install `postgresql-client-16` on the app server.
3. Add the daily cron line. A week later, run `backup:restore-test` against an empty scratch database.

## Known limitations
- The phishing checks are heuristics. They catch common tricks but not everything, and they can occasionally warn about legitimate mail (for example a company whose name contains a brand name).
- The lookalike list covers about 25 commonly imitated brands. It's easy to extend in `src/security/phishing.ts`.
- Each backup is uploaded in a single request (up to 5 GB). For larger databases, use the host's managed backups (Supabase and Neon both have them) or pgBackRest.
- With a hosted database, the provider's own point-in-time recovery is the main safety net. These backups are an extra copy you control. **After any provider-side restore, run `backup:reapply-deletions` too.**
